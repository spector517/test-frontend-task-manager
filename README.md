# Менеджер задач — frontend-прототип

SPA-канбан для команды: **Vue 3 + TypeScript + Pinia + Vite + Element Plus**, архитектура — **Feature-Sliced Design**. Бекенда нет: API имитируется моками с задержкой.

## Требования

- **Node.js 22** (`>=22.12.0`; нужная версия указана в `.nvmrc` и `package.json → engines`)
- npm 10+

> Линтер FSD (Steiger) требует Node `>=22.18` — на более старых 22.x он не запустится, но на сборку и запуск приложения это не влияет.

## Запуск

```bash
nvm use            # переключиться на Node 22 (если используется nvm)
npm ci             # установить зависимости
npm run dev        # dev-сервер: http://localhost:5173
```

## Скрипты

| Команда             | Что делает                                                 |
| ------------------- | ---------------------------------------------------------- |
| `npm run dev`       | dev-сервер Vite с HMR                                      |

### Имитация ошибок сервера

Чтобы увидеть error-state (сообщение об ошибке и кнопку «Повторить»), создайте `.env.local`:

```
VITE_MOCK_FAIL_RATE=0.3
```

Значение — доля запросов (0..1), которые завершатся ошибкой. По умолчанию `0`.

## Функциональность

**Список задач (`/tasks`)** — канбан из трёх колонок («К выполнению», «В работе», «Готово»):

- карточка: название (ссылка на задачу), статус, приоритет, исполнитель, дата создания;
- «Создать задачу» — диалог с формой (статус по умолчанию `todo` и в форме не выводится); после создания — переход на `/tasks/:id`;
- клонирование (копируется всё, включая комментарии и дату создания; меняется только `id`);
- удаление с подтверждением;
- фильтры по названию, статусам и приоритетам (одновременно, по «И») и «Сбросить фильтры»;
- **drag & drop** карточки в другую колонку открывает диалог с обязательным комментарием: статус меняется только после подтверждения, комментарий добавляется в начало списка; при отмене карточка остаётся на месте. На телефоне и с клавиатуры то же действие доступно через кнопку «Статус» на карточке.

**Карточка задачи (`/tasks/:id`)**:

- режим чтения всех полей, кроме `id`; «Редактировать» — диалог с формой, «Сохранить» — сохраняет и закрывает диалог;
- «Назад» — на список задач; несуществующая задача — уведомление и редирект на `/tasks`;
- комментарии: создание, редактирование, удаление, сортировка по времени («Сначала новые / Сначала старые»).

**Общее**: лоадеры на время имитации сети (2 с), ошибки загрузки показываются с кнопкой «Повторить», ошибки валидации — под полями форм, результат операций — toast-уведомлениями. Вёрстка адаптирована под мобильные экраны; цвета текста подобраны с контрастом не ниже 4.5:1 (WCAG AA).

## Архитектура

```
src/
├── app/        # точка входа, роутер (hash history), глобальные стили и тема
├── pages/      # task-list, task-card — композиция виджетов и фич
├── widgets/    # kanban-board, task-details, comment-thread
├── features/   # task-create, task-edit, task-delete, task-clone, task-filter,
│               # task-change-status, comment-manage
├── entities/
│   └── task/   # типы, Pinia store, Yup-схемы, mapper DTO ⇄ domain, repository, UI карточки
└── shared/     # мок-API и DTO, утилиты (toast, даты, адаптер Yup → el-form), базовые UI
```

- Импорты идут строго сверху вниз (`app → pages → widgets → features → entities → shared`), каждый слайс открывает наружу только свой `index.ts`. Соблюдение проверяет Steiger (`npm run lint:fsd`).
- **Данные.** `shared/api/task-api.ts` — мок-бекенд в формате DTO (`created_at`, комментарии в старом `string[]` и новом `{ text, created_at }` форматах). `entities/task/api/task-mapper.ts` приводит DTO к доменной модели (`createdAt`, у каждого комментария есть `id` и дата), `task-repository.ts` отдаёт наружу только доменные типы.
- **Состояние.** `useTaskStore` хранит превью задач (`tasks`) для канбана и полную карточку (`current`) для детальной страницы. После каждой мутации синхронизируются оба представления. Загрузки пишут `loading/error` в store, мутации пробрасывают ошибку вызывающему коду (для toast).
- **Валидация.** Yup-схемы в `entities/task/model/schema.ts`; адаптер `shared/lib/validation/yup-to-el-rules.ts` превращает схему в правила `el-form`, поэтому ошибки показываются под полями. Дубликат названия проверяется по списку задач из Pinia (`store.tasks.some(t => t.title === title)`); при редактировании текущая задача исключается.

## Принятые решения

- **Фильтрация на клиенте.** Список загружается один раз, фильтр — `computed` над `store.tasks`: так фильтры работают мгновенно, без 2-секундной задержки на каждое изменение. `taskApi.getAll(filters)` при этом полностью реализует серверную фильтрацию по всем трём полям.
- **Комментарии старого формата** (строки из исходных моков) получают дату создания задачи и детерминированный `id` (`<taskId>:legacy:<index>`). Мок при первом изменении переводит их в объектный формат с теми же `id`, поэтому их тоже можно редактировать и удалять.
- **Клон** получает то же название, что и оригинал: ТЗ требует менять только `id`. Проверка дубликатов относится к формам создания и редактирования.
- **Исполнитель** — поле email с подсказками из уже известных исполнителей (можно ввести новый адрес).
- **Задержки.** Чтение, создание, клонирование и удаление — 2 с (как в ТЗ); точечные изменения (редактирование, смена статуса, комментарии) — 300 мс, как `update` в ТЗ.
- **Element Plus подключён целиком** — для прототипа это проще, чем импорт по требованию; библиотека вынесена в отдельный чанк.
- **Роутер** соответствует ТЗ; страницы импортируются через public API слайса (`@/pages/task-list`), а неизвестные адреса перенаправляются на `/tasks`.

## Тесты

`npm test` — 54 теста:

- `task-mapper` — `created_at → createdAt`, нормализация `string[]` и смешанных комментариев, отсутствие `comments`;
- `schema` — границы длины названия и описания, приоритет вне списка, email, дубликаты (с исключением текущей задачи);
- `filter-tasks`, `sort-comments` — каждый фильтр и их комбинация, сортировка asc/desc;
- `task-store` — смена статуса с комментарием в начале, клон, синхронизация `tasks` и `current`, ошибки мутаций;
- `task-api` — задержка, фильтры, клон, миграция старых комментариев;
- `TaskFormFields` — ошибки валидации под полями формы.
